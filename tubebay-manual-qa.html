TubeBay Blocks — Manual QA Guide

Click-through testing for the two new Gutenberg blocks, the lightbox, popup widths, and the loosened video-library permission. Everything below was written against the working-tree source, not from memory.

Site: http://localhost WordPress 7.1 Theme: Storefront tubebay + tubebaypro active 21 scenarios
0 / 21 done

What changed

Two brand-new Gutenberg blocks in the free plugin — tubebay/video ("TubeBay Video") and tubebay/video-button ("TubeBay Video Button") — plus a shared frontend lightbox, per-block popup width controls, and a REST permission change that lets anyone with edit_posts browse the channel library (pinned to the cached list unless they are a TubeBay admin). Build tooling changed too: the blocks are extra webpack entry points and build.sh now runs a second i18n pass.

Read scenario 1 before anything else. The plugin version constant was not bumped (still 1.2.0) while the block JavaScript and CSS were edited today. Every block asset URL therefore still ends in ?ver=1.2.0, so a warm browser cache will happily serve you yesterday's lightbox code and you will chase phantom bugs. Disable cache first.

9.

Where to go
http://localhost/tubebay-thumbnail-popup-demo/
What to click

Put the mouse down. Use only the keyboard for this whole scenario.

  1. Click once on the page background to give the document focus, then press Tab repeatedly until the play badge on the thumbnail has a visible white focus ring.
  2. Press Enter.
  3. Run document.activeElement.className in the console (or just look for the focus ring).
  4. Press Tab three or four times.
  5. Press Esc.
  6. Run document.activeElement.className again.
  7. Reopen with Enter, then close by pressing Enter on the × button.
  8. Reopen once more and this time click the dark area outside the player.
What you should see
  • The play badge takes focus and shows a white outline; the badge also turns red.
  • Enter opens the popup, and within a fraction of a second focus lands on the close button — document.activeElement.className contains tubebay-lightbox-close.
  • Tabbing never leaves the dialog. Focus stays on the close button no matter how many times you press Tab or Shift+Tab. It must not land on links in the page behind the overlay. (Only ever landing on the close button is intended — see the "expected, do not report" list.)
  • Esc closes the popup, the audio stops immediately, and document.activeElement.className now contains tubebay-block-play — focus is back on the thumbnail you came from.
  • Closing via the × button restores focus the same way.
  • Clicking the dark backdrop closes it; clicking the player itself does not.
  • After every close, document.querySelectorAll('.tubebay-lightbox-overlay iframe').length is 0 — the player is destroyed, not just hidden.
Why it matters
A modal a keyboard user cannot escape from, or that dumps them back at the top of the page, is a hard accessibility failure.

E. Resilience

21.

Where to go
http://localhost/tubebay-blocks-demo/
What to click

YouTube does not publish a maxresdefault thumbnail for every video, so the block ships a fallback. Force it from the Console:

  1. Run: 
    const t = document.querySelector('.tubebay-block-facade__thumb');
console.log('fallback is:', t.dataset.fallback);
t.src = 'https://i.ytimg.com/vi/ZZZZZZZZZZZ/maxresdefault.jpg';
  2. Wait a moment, then run: 
    console.log(t.src, t.dataset.tubebayFallbackApplied);
What you should see
  • data-fallback is a real .../hqdefault.jpg URL.
  • After the failed load, t.src has switched itself to that fallback URL and t.dataset.tubebayFallbackApplied is "1".
  • The thumbnail is visibly back — no broken-image icon, no empty black box.
  • Running the same broken URL a second time does not loop; the flag stops it.
Why it matters
These are static blocks — there is no server-side render pass that could ever correct a bad thumbnail after the fact.

Known issues and expected failures

Everything here was confirmed by reading the source. Please do not file these as new bugs.

  • BugAn administrator is told they are not an administrator

    Whenever the video library route reports that searching is off-limits, the picker disables Sort by and shows "Showing the most recent videos. Sorting the full channel needs a TubeBay administrator." The server also sends that flag when no channel is connected — regardless of who is asking. So an administrator with a disconnected channel is told they need to be an administrator.

    app/Api/YouTubeController.php (the not-configured early return sends can_search: false) · src/blocks/shared/VideoPicker.tsx (disables on hasFetched && !canSearch).

  • BugThe lightbox's mobile full-width rule never applies

    assets/css/blocks/tubebay-blocks.css has a @media (max-width: 768px) rule setting the popup to width: 100%, but the view script writes an inline width on every open, including when the author left the width empty. Inline styles win, so narrow screens get 90% and never the intended 100%. Cosmetic only — the popup still fits and works.

    assets/js/blocks/tubebay-blocks-view.js, applySize().

  • EnvironmentVersion constant not bumped — block assets are cached under the old version

    Both block.json files and every new @since tag say 1.3.0, but the plugin header and TUBEBAY_VERSION still say 1.2.0. Since tubebay-blocks-view.js and the block CSS are versioned by that constant, edits made to them today do not bust anyone's cache. This is a release-process item, and the reason scenario 1 exists.

  • EnvironmentThis site reports "disconnected" while the library actually works

    tubebay_connection_status is not set on this install, so it defaults to inactive and the Library screen says "Your YouTube library is currently disconnected." — yet an OAuth refresh token is present and a 19-video cache is warm, so the block picker lists videos perfectly well. This mismatch is a pre-existing, already-documented data-integrity issue, not something the blocks introduced.

    Documented in the repo's CLAUDE.md under "Known issues".

  • EnvironmentThe cached video list expires soon

    The tubebay_videos_cache transient on this install expires around 2026-08-31 00:12. After that the picker may return nothing, because tubebay_channel_id is empty here and a live refresh cannot be built from it. Fall back to the manual-paste path (scenario 11), which is channel-independent by design.

  • By designEscape stops working once you click into the player

    The YouTube player is a cross-origin iframe: once focus is inside it, every keypress — Esc included — is delivered to YouTube's document and never reaches the page. Close with the × button or the backdrop instead. The alternative (making the iframe a tab stop) would create a keyboard trap, which is a worse failure.

  • By designTab inside the popup only ever lands on the close button

    The dialog deliberately has exactly one tab stop. Pressing Tab repeatedly looking like "nothing happens" is the correct behaviour — what matters is that focus never escapes to the page behind the overlay.

  • By designInline playback drops focus into the player

    After pressing Enter on an inline (non-popup) facade, focus is moved into the YouTube iframe so the keyboard is not stranded on <body>. Tabbing back out of it may feel unusual — same cross-origin constraint as above.

  • By designThe editor preview is not clickable

    Clicking a video block's thumbnail in the editor selects the block instead of playing anything. The preview has pointer-events: none on purpose.

  • By designThe saved aria-label differs from the live one

    View-source shows aria-label="<video title>", but the live DOM shows aria-label="Play video: <video title>" — the script upgrades it at runtime. A translated label cannot be frozen into post content without invalidating the block for authors in other languages. Untitled videos (any manually pasted URL) get plain "Play video".

  • By designThe deprecation lists are empty

    Both deprecated.ts files are intentionally empty on this first release. It is the wiring, not an omission. It does mean scenario 17 is the only guard against saved-markup drift, so treat any validation warning there as serious.
